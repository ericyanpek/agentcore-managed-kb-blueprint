# ADR-004: 删除比例超限采取硬失败而非人工审批暂停

- 状态：已接受
- 日期：2026-08-18

## 背景

发布时若待删除文档数超过前一版本文档总数的一定比例（默认阈值 0.5，即 50%），有必要
拦截，防止误操作清空知识库。问题在于：拦截后是直接报错让操作者重新发起，还是暂停
执行等待人工审批后继续？

此外，在实现过程中发现了两处相关缺陷需要一并修正：
1. 原实现以删除后文档数为分母计算删除比例，导致全量删除时比例为 0%，保护逻辑
   完全失效。
2. 阈值缺乏范围校验，超出 `[0, 1]` 的值会使保护逻辑静默失效（高于 1）或阻断
   所有发布（低于 0）。

## 决策

删除比例超限时，状态机**硬失败**（进入 `FailRelease`），不写入任何摄入或删除操作，
不修改 `POINTER`。操作者确认意图后携带 `allowBulkDeletion=true` 重新发起一次新的
执行。

同步修正两处缺陷：
- 分母改为**本次发布前**的 Manifest 文档总数（`previousDocumentCount`）。全量删除
  时分母为发布前文档数，比例正确计算为 100%，而非删除后的 0%。
- 阈值在门禁函数入口处校验必须位于 `[0, 1]`（含边界）。超范围值直接抛出
  `ValueError`，在状态机启动前即可发现配置错误。

## 理由

**硬失败不引入审批回调基础设施。** Task Token 暂停模式需要一个审批回调通道（例如
SNS + 邮件 + Lambda 处理 TaskToken），这套基础设施本身的可靠性需要测试和运维。
硬失败只依赖操作者重新发起执行，基础设施零增加。

**两次执行记录保留审批痕迹。** 第一次执行因超限失败，状态为 `FAILED`，保留
执行输入与失败原因。第二次执行携带 `allowBulkDeletion=true`，状态为 `ACTIVE`，
执行输入中显式记录了操作者的授权意图。审计时两条记录共同说明全量删除经过人工确认。

**长时间 Task Token 暂停消耗执行生命周期。** Step Functions Standard 类型单次执行
最长一年，但长时间持开执行意味着状态机占用计费时间、占用执行配额，且若超时或被清理
则审批动作丢失。硬失败立即释放执行，无此问题。

**分母修正是正确性修复，不是行为变更。** 原实现（`scripts/22_incremental_ingest.py`）
以删除后文档数为分母，导致删除 100 个文档后剩余 0 个时，比例 = 0/(100-100) = 0%，
保护完全不起作用。`gates.py` 中 `evaluate_deletion_ratio` 明确使用
`previous_document_count` 作为分母并在函数注释中说明了原因。

**初次发布（无前序 Manifest）的分母为零**，此时删除集合必然为空（没有文档可删），
`gates.py` 中对该边界情形的处理是：若 `previous_document_count == 0` 且
`deleted_count == 0`，直接通过；若 `previous_document_count == 0` 且
`deleted_count > 0`，抛出 `ValueError`（不应出现的状态）。

## 后果

- 操作者在超限情况下必须明确重新发起执行并传入 `allowBulkDeletion=true`，无法在
  同一次执行中"批准后继续"——这是有意的摩擦，确保大规模删除经过显式确认。
- 删除比例保护对全量删除（如清空语料库）现在有效，不再因分母为零而静默通过。
- 阈值的 `[0, 1]` 校验确保配置错误在本地单元测试阶段即可发现（pytest 覆盖了
  边界值 `threshold=-0.1` 和 `threshold=1.5`）。
- 若后续需要引入审批工作流（例如与 OA 系统集成），可将硬失败改为 Task Token 暂停；
  数据模型与状态机拓扑不需要变动，只需替换门禁 B 的分支逻辑。

## 备选方案

| 方案 | 落选理由 |
| --- | --- |
| Task Token 暂停 + SNS 通知 | 需要审批回调通道（SNS Topic、订阅、Token 传递机制），基础设施复杂度不匹配参考实现定位；长时暂停持续占用执行生命周期 |
| 仅告警不阻断（原有行为） | 原脚本实现已确认此方式存在问题：告警被忽略，删除操作仍然执行；不满足"保护知识库内容"的目的 |
| 要求操作者修改配置文件后重部署 | 流程过重；配置变更可能引发无关资源替换，且不留下"本次发布经授权"的细粒度执行记录 |
